# AI 기초 발표 스크립트·워크북 화면 안내

AI 기초 40분 / 워크북 화면 설명 20분
자료실: https://bit.ly/impact_ir

## 1부 발표자료

### 1쪽. AI 기초와 회사 업무환경 구축 (1분)

오늘은 IR 목차를 다시 배우는 시간이 아닙니다. 앞 강의에서 이해한 사업과 투자 논리를 AI와 구체화하는 방법을 살펴봅니다. 목표는 긴 프롬프트를 외우는 것이 아니라 회사자료, 작업 기준, 실행 역할을 준비하는 것입니다. 먼저 40분 동안 도구와 모델, 추론, 스킬과 에이전트를 설명합니다. 이후 20분은 웹 워크북을 열고 제공 파일과 사용 위치를 설명합니다. 현장에서 설치하거나 생성 결과를 기다리는 시연은 하지 않습니다.

### 2쪽. 사람과 AI의 역할 (2분)

AI에게 일을 맡기려면 먼저 내 사업에서 바꿀 수 있는 것과 유지할 것을 알려줘야 합니다. 자료 정리와 조사, 계산, 초안, 교정은 맡길 수 있습니다. 그러나 고객을 누구로 바꿀지, 가격을 얼마로 확정할지, 어떤 투자 조건을 받아들일지는 대표가 결정합니다. AI가 문장을 매끄럽게 만들었다고 실제 고객이나 매출이 생기지는 않습니다. 패키지에서는 기업정보, 사업가정, 의사결정을 분리해 이 경계를 남깁니다.

### 3쪽. 프로그램·모델·추론 설정 (2분)

Cursor와 Gemini를 같은 종류의 제품으로 비교하면 혼란스럽습니다. 프로그램은 파일을 열고 도구를 실행하는 환경이고, 모델은 그 환경에서 이해와 생성을 수행합니다. 같은 프로그램에서도 사용 가능한 모델이 여러 개일 수 있습니다. 추론 설정은 또 다른 선택입니다. 웹 워크북의 도구 선택은 해당 설정 파일을 만들기 위한 것이며 실제 AI 프로그램의 모델을 바꾸지는 않습니다. 이용 가능한 모델과 단계는 계정·제품·버전에 따라 확인합니다.

### 4쪽. 웹과 설치형 작업환경 (2분)

웹에서도 파일을 읽고 프로젝트 지침을 사용할 수 있습니다. 이 강의가 설치형을 권장하는 이유는 회사자료와 작업 기준, 조사와 제작 결과를 같은 작업 폴더에서 반복 관리하기 좋기 때문입니다. 로컬 설치와 로컬 모델 실행은 다릅니다. 프로그램은 내 컴퓨터에 있어도 모델 처리에는 클라우드를 사용할 수 있습니다. 계약서와 개인정보를 제공하기 전에 회사 방침과 해당 서비스의 전송·보관 조건을 확인해야 합니다.

### 5쪽. 앱·편집기·CLI (1분)

CLI는 명령줄 인터페이스입니다. 터미널에서 프로그램을 시작하지만 실행 후에는 자연어로 지시할 수 있습니다. 앱이나 편집기는 파일을 눈으로 확인하기 편합니다. 도구 하나가 여러 사용 형태를 제공할 수도 있으므로 특정 브랜드를 한 형태로만 기억할 필요는 없습니다. 초보자는 설치와 로그인, 작업 폴더 선택, 결과 파일 확인을 먼저 익히면 됩니다.

### 6쪽. 설치와 기본 설정 (2분)

제공 패키지를 압축 해제한 뒤 회사 폴더를 지정하고 설정 프롬프트를 전달합니다. 기존 회사 폴더가 있다면 패키지 위치를 별도로 알려줘도 됩니다. AI는 안내된 프로젝트 경로에 파일을 배치하고 기존 설정을 비교합니다. 로그인, 권한 승인, 재시작은 사람이 해야 할 수 있습니다. 구독 계정 로그인과 API 키 연결은 다른 이용 경로이며 요금이 자동으로 동일하게 적용된다고 생각하면 안 됩니다. 이 수업은 API 키 입력을 필수로 하지 않습니다. 설정 완료 후에는 실제로 어떤 도구가 작동하는지 확인합니다.

### 7쪽. 모델 선택 기준 (2분)

모든 작업에 가장 무거운 모델을 사용할 필요는 없습니다. 같은 회사소개서에서 항목을 추출하는 일과 여러 사업가정의 모순을 찾는 일은 난도가 다릅니다. 모델 비교 시 같은 파일과 같은 완료 기준을 사용합니다. 오류, 누락, 시간과 사용량을 비교해야 결과가 얼마나 달라졌는지 알 수 있습니다. 모델 이름만으로 검색이나 파일 제작이 가능한 것도 아닙니다. 사용 프로그램에 해당 도구가 연결돼 있는지 함께 확인합니다.

### 8쪽. GPT 모델별 선택 기준 (2분)

공식 모델 구분을 업무에 연결한 선택 예시입니다. Astra는 어려운 문제, Sol은 성능과 비용의 균형, Luna는 범위가 분명한 반복 작업을 출발점으로 봅니다. 실제 프로그램에서 이 모델을 모두 선택할 수 있다는 뜻은 아닙니다. 프롬프트에는 원하는 결과와 제한 범위, 확인할 근거를 명확히 줍니다. 전문가 역할을 길게 선언하는 것만으로 품질이 보장되지 않습니다. 추론을 길게 써달라고 하기보다 결론, 확인 근거, 계산과 미해결 항목을 요구합니다. 모델 업데이트 후에도 회사자료와 승인된 결정은 유지하고 동일 과업으로 결과를 비교합니다.

참조: https://developers.openai.com/api/docs/models / https://developers.openai.com/api/docs/guides/reasoning-best-practices

### 9쪽. Claude 모델별 선택 기준 (1분)

Claude도 하나의 모델이 아닙니다. 공식 포지션을 확인한 뒤 자신의 작업에 맞춰 비교합니다. 역할 지시는 여전히 관점과 톤을 지정할 때 쓸 수 있습니다. 다만 투자자 관점이라고만 쓰지 말고 무엇을 확인할지 함께 적습니다. 긴 자료에서는 문서와 출처를 구분하고 작업 질문을 명확히 배치합니다. 스킬에 이미 포함된 검토 기준을 매번 프롬프트에 복사할 필요는 없습니다. 이 표의 작업 배분은 공식 성능 보증이나 브랜드 간 순위가 아니라 적용 출발점입니다.

참조: https://platform.claude.com/docs/en/models/overview / https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices

### 10쪽. Gemini 모델별 선택 기준 (1분)

Pro와 Flash는 이름만으로 세대가 다른 모델의 성능 순서를 단정할 수 없습니다. Preview 여부와 현재 이용 환경도 확인합니다. 문서와 이미지, 표를 함께 제공할 때는 어느 파일의 어느 부분을 분석할지 지정하는 것이 중요합니다. 표를 읽는 능력과 시장 사실이 맞는지는 다른 문제입니다. 읽은 값도 원문과 대조하고, 시장 수치는 출처의 정의와 기간을 확인합니다. 워크북의 Gemini 가이드에는 별도 공식 안내와 프롬프트 예시가 있습니다.

참조: https://ai.google.dev/gemini-api/docs/models / https://ai.google.dev/gemini-api/docs/prompting-strategies

### 11쪽. 추론 설정과 답변 길이 (2분)

Low, Medium, High는 이해를 위한 공통 표현입니다. 모든 모델과 프로그램이 동일한 단계나 의미를 제공하는 것은 아닙니다. 추론 설정은 문제 해결에 쓰는 노력이고 답변의 분량은 별도 요구입니다. 높은 노력으로 분석하되 결과는 한 페이지로 요청할 수 있습니다. 반대로 길고 자세한 답이 정확한 답을 뜻하지 않습니다. 채팅에 high로 해달라고 쓰는 것만으로 실제 프로그램의 설정이 바뀌는지도 확인해야 합니다.

### 12쪽. 교육자료실 (0.5분)

화면의 주소로 교육자료실에 접속합니다. 지금은 접속만 확인하고, 설치와 작업 실행은 강의 후 진행해도 됩니다. 자료실에서 사용할 프로그램을 선택해 전체 패키지를 한 번 받고 설정문을 복사합니다. 스킬과 에이전트는 패키지에 포함되어 있어 개별 프롬프트를 순서대로 내려받을 필요가 없습니다.

### 13쪽. 기획 검토 후 실행, 자동 승인은 제한적으로 (3.5분)

처음부터 모든 것을 한 번에 만들라고 하기보다, 자료와 목적을 전달하고 기획안을 먼저 요청합니다. 예를 들어 “구성과 필요한 조사, 수정할 파일, 검토 기준을 먼저 제안해줘. 내가 확인하기 전에는 제작하지 마”라고 요청합니다. 내용을 확인한 다음 “이 범위로 실행해줘”라고 전환합니다.

계획을 승인하는 것, 도구 실행을 승인하는 것, 파일·네트워크 접근 권한은 서로 다릅니다. 계획 모드도 자료 조회나 계획 파일 저장을 할 수 있어 아무 행동도 하지 않는 상태로 이해하면 안 됩니다. 프롬프트의 요청만으로 프로그램의 실제 권한 설정이 바뀌지도 않습니다.

Codex는 /plan과 /permissions를 구분합니다. auto_review는 일부 승인 요청을 검토 에이전트가 판단하며 Sandbox의 접근 경계와 별도입니다. Claude Code의 acceptEdits는 파일 편집·일부 파일 작업 허용이고 auto는 위험 판단을 거치는 모드입니다. bypassPermissions는 승인 절차를 건너뛰는 강한 설정으로 같은 의미가 아닙니다. Cursor의 Auto-review는 검토를, Allowlist는 지정한 반복 작업 허용을 뜻합니다. Run Everything은 검토·샌드박스 보호가 없는 설정입니다. Antigravity는 /plan과 Implementation plan을 사용하며 계획 검토와 실행 권한 설정을 구분합니다. macOS·Linux의 Default/Request Review/Turbo와 Windows의 Request Review/Proceed in Sandbox/Always Proceed처럼 운영체제별 명칭과 동작도 다릅니다.

이는 모델 이름보다 실행 프로그램·버전·OS·조직 정책의 설정에 가깝습니다. 일부 자동 승인 기능은 지원 모델이나 계정에 따라 제공 여부가 달라집니다.

자동 승인은 반복 확인을 줄여 편하지만 오판 가능성이 있습니다. 한두 번 결과가 좋았다는 이유로 전체 접근을 주지 않습니다. 계획·변경 대상·허용 폴더·복구 방법을 확인한 뒤 검증된 반복 작업에만 적용합니다. 자동 승인과 권한 확대가 결합하면 원본 삭제나 비공개 자료 전송까지 실행될 위험이 커집니다. 백업 또는 버전 기록을 유지하고, 삭제·외부 업로드·결제·회사정보 확정은 사람이 별도로 확인하는 기준을 둡니다. 이 권장 기준은 제품의 기본 설정과 구분해서 설명합니다.

참조: https://learn.chatgpt.com/docs/developer-commands / https://learn.chatgpt.com/docs/sandboxing / https://code.claude.com/docs/en/permissions / https://cursor.com/docs/agent/plan-mode / https://cursor.com/docs/agent/security/run-modes / https://antigravity.google/docs/implementation-plan / https://antigravity.google/docs/agent-settings

### 14쪽. 컨텍스트와 참조 파일 (1분)

폴더 안에 파일이 있다는 것과 AI가 실제로 읽었다는 것은 다릅니다. 컨텍스트는 이번 판단에 제공된 정보이며 모델이 다룰 수 있는 양에는 한계가 있습니다. 토큰은 글자 수와 완전히 같지 않은 처리 단위입니다. 대화를 오래 이어가는 것만으로 회사자료를 안전하게 관리할 수는 없습니다. 승인된 자료를 파일로 남기고 필요한 파일을 다시 읽게 하는 이유입니다. 스캔 문서나 복잡한 표를 읽지 못한 경우도 확인해야 합니다.

### 15쪽. 프롬프트: 이번 작업의 지시 (2분)

이 지시에는 이번 목적과 대상, 발표 시간, 승인 지점이 들어 있습니다. 조사 방법, 계산 기준, 문장 교정 기준을 길게 반복하지 않아도 패키지의 스킬이 담당합니다. 단, 회사자료를 어디에서 읽을지와 무엇을 만들지는 명확해야 합니다. 기존자료 정리, 사업기획, 리서치, IR 제작의 시작 프롬프트를 제공하며 세부 프롬프트는 특정 작업을 다시 할 때 사용합니다. 모델별 작성 요령은 구조와 예시의 조정에 활용하고 사업 사실은 바꾸지 않습니다.

### 16쪽. 스킬: 반복 작업의 절차와 기준 (2분)

스킬은 자주 쓰는 긴 프롬프트를 파일로 보관하는 데서 끝나지 않습니다. 언제 적용할지, 어떤 자료와 기준을 읽을지, 무엇을 결과로 남길지 정합니다. 제공 스킬은 다섯 파일로 구성되며 본문에서 기업정보 양식, 기획 작성양식, 검토 기준으로 연결됩니다. 리서치와 계산도 이 안의 작업 모드입니다. 회사의 실제 자료는 스킬 폴더에 넣지 않고 기업정보와 작업 폴더에 따로 보관합니다. 다른 회사에서도 같은 기준을 재사용하기 위해서입니다.

### 17쪽. 에이전트와 작업 연결 (2분)

에이전트는 맡은 목표를 수행하면서 모델과 도구, 스킬을 사용하는 실행 주체입니다. 워크플로는 이 작업들이 이어지는 순서와 조건입니다. 이 패키지에서는 기획·제작이 전체 진행을 조율합니다. 조사 질문을 리서치·분석에 넘기고 결과를 기획에 반영한 뒤 검토 역할에 대조를 요청합니다. 도구에서 별도 에이전트를 지원하지 않으면 같은 AI가 역할을 순차 적용합니다. 역할 파일이 존재한다는 이유만으로 독립 실행됐다고 보고하지 않도록 설정합니다.

### 18쪽. MD와 회사정보 관리 (2분)

Markdown은 제목과 목록, 표를 텍스트로 표현하는 형식입니다. 문법을 모두 외울 필요는 없습니다. 기존 회사소개서를 주고 이 양식에 맞춰 채워달라고 요청하면 됩니다. 중요한 것은 AI가 어떤 파일을 읽었고 무엇을 사실로 정리했는지 확인하는 일입니다. 처음에는 이 구조화된 파일 묶음이 회사정보 DB 역할을 할 수 있습니다. 자료를 MD로 바꿨다고 모델을 학습시킨 것은 아니며 원본 증빙을 지워도 된다는 뜻도 아닙니다.

### 19쪽. 패키지 구성과 적용 확인 (1분)

ZIP을 받고 폴더를 여는 것으로 끝나지 않습니다. 설정 프롬프트로 사용하는 도구의 프로젝트 경로에 스킬과 역할을 적용하게 합니다. 기존 설정은 비교하고 회사자료는 보존합니다. 설정확인에는 실제 읽기와 쓰기, 스킬 인식, 에이전트 실행 방식, 검색과 원문 열람, 계산과 제작 도구의 가용성이 남아야 합니다. 등록 여부를 확인하지 못했다면 적용 대기 상태로 받아야 합니다. 스킬을 제공한다고 검색 도구나 PPT 제작기가 자동 설치되는 것은 아닙니다.

### 20쪽. 리서치: 조사 질문과 원문 근거 (2분)

다회용기 서비스라면 친환경 시장이 성장하는가라는 큰 질문만 조사하지 않습니다. 행사 운영사가 어떤 업무를 외주로 맡기는지, 현재 대안과 비용은 무엇인지, 제공 가능한 지역의 구매자가 누구인지 조사합니다. 공식 제품 페이지는 제공 기능과 가격의 근거가 될 수 있지만 효과를 독립적으로 검증해주지는 않습니다. 원문을 열 수 없으면 미확인으로 남깁니다. 근거대장은 출처와 주장, 사용 위치를 연결합니다. 반대 자료가 나오면 사업 가설을 바꿀 수 있어야 합니다.

### 21쪽. 조사 근거와 계산의 연결 (1분)

AI에게 숫자 하나만 받지 말고 어떤 입력으로 계산했는지 받아야 합니다. 고객 수와 구매량, 단가의 지역과 기간이 맞아야 합니다. 영업 전환과 처리 역량이 불명확하다면 목표로 구분합니다. 산식이 맞다는 것과 그 가정이 현실적이라는 것은 별개의 판단입니다. 근거가 바뀌면 계산과 이를 사용한 IR 페이지, 차트도 함께 갱신해야 합니다.

### 22쪽. AI로 IR 한 편 제작 (2분)

앞에서 설정한 환경이 실제로 쓰이는 장면입니다. 사용자는 대상 투자자와 목적, 발표 시간을 전달합니다. 에이전트는 승인된 회사자료를 읽고 부족한 조사와 계산을 보완합니다. 구성안에는 제목뿐 아니라 실제 본문과 근거, 시각화 계획이 있어야 합니다. 대표가 방향을 확인하면 제작으로 넘어갑니다. 제작 도구가 없으면 원고와 시각화 명세까지만 만들었다고 구분해 보고합니다. 하우스와 펀드, 포트폴리오 조사로 강조점은 바꿀 수 있지만 회사 사실을 바꾸지는 않습니다.

### 23쪽. 검토·수정·재검토 (2분)

검토는 맞춤법 검사만이 아닙니다. 같은 숫자가 시장 계산과 매출 계획, 원고와 차트에서 일치하는지 확인해야 합니다. 표현 문제를 해결하려고 사업 사실을 바꾸면 안 됩니다. 원인에 맞는 단계로 돌아가고 변경이 영향을 주는 부분까지 다시 봅니다. 반복해도 새 근거가 없으면 조사나 현장 검증이 필요한 상태로 남깁니다. 내부 문구와 메모는 제출본에서 제거하지만 중요한 가정과 위험 조건은 보존합니다. 강사님의 실제 문구 교정 캡처는 별도 화면 설명에서 사용할 수 있으며 이 자료에 임의 사례를 추가하지 않았습니다.

### 24쪽. 재사용과 업데이트 (1분)

같은 회사자료를 다음 IR과 사업계획에서도 재사용합니다. 새 실적이 생기면 자료를 추가하고 대표 확인을 거쳐 갱신합니다. 스킬과 에이전트의 업데이트는 별개입니다. 웹에 새 버전이 올라와도 로컬 설치본이 자동으로 바뀌지는 않습니다. 새 패키지를 비교하고 회사정보와 맞춤 설정을 보존한 채 적용해야 합니다. 이제 워크북을 열고 패키지, 회사자료 준비, 작업 시작, 결과 확인 위치를 20분 동안 설명합니다.

## 2부 워크북 화면 설명

### 패키지 구성 (4분)

- 화면: #start → #package
- 보여줄 내용: 작업환경 첫 화면, 도구 선택, ZIP 구성, 세 역할과 스킬
- 확인할 결과: 00_설정의 스킬·에이전트와 01~06 작업 폴더 구분

웹은 AI 실행기가 아니라 준비 자료실입니다. 스킬에 반복 기준이 있고 에이전트 지침이 필요한 작업을 연결합니다. 사용하는 도구를 선택해 ZIP을 받습니다. 회사정보를 웹에 입력하지 않아도 빈 양식 패키지를 받을 수 있습니다.

### 설정 적용 (4분)

- 화면: #package → 작업환경 설정
- 보여줄 내용: 설정 프롬프트, 적용 경로, 설정확인 항목
- 확인할 결과: 05_검토기록/설정확인.md

설치·로그인 후 회사 폴더와 패키지 위치를 지정합니다. AI에게 설정 적용을 맡기고 사람은 권한 승인과 재시작을 처리합니다. 스킬 인식, 독립 또는 순차 역할 실행, 검색·원문 열람·계산·제작 도구를 실제 확인해야 합니다. 여기서는 실행하지 않고 설정 요청과 확인 결과의 위치를 설명합니다.

### 회사자료 준비 (4분)

- 화면: #manual → #workbook 또는 기존자료 정리
- 보여줄 내용: 기존자료 경로, 기업정보 양식, 확인 상태, MD 다운로드
- 확인할 결과: 기업정보_검토안.md·기업정보_확인사항.md·승인된 기업정보.md

회사소개서나 앞 강의 워크북이 있으면 해당 파일을 넣고 정리하게 합니다. 웹 항목을 다시 채우지 않아도 됩니다. AI는 검토안과 충돌·누락을 반환합니다. 대표 확인 후 회사정보로 사용하며 자료가 없다면 웹에서 최초 작성합니다. 웹에서 로컬 MD를 자동으로 불러오거나 동기화하지는 않습니다.

### 작업 시작 (4분)

- 화면: #start → 사업기획 / 리서치 / IR 제작
- 보여줄 내용: 세 시작 프롬프트, 이번 조건, 스킬의 적용 모드
- 확인할 결과: 조사계획·근거대장·계산·IR 구성안·제작본

전체 목적을 한 번 지정하면 필요한 조사와 계산이 연결됩니다. 리서치만 요청하면 조사 결과까지만 받습니다. IR 제작은 구성안 확인 후 제작합니다. 개별 프롬프트는 경쟁사만 다시 조사하거나 숫자만 재계산할 때 쓰는 보조 기능입니다. 모두 순서대로 복사하지 않습니다.

### 결과 확인·업데이트 (4분)

- 화면: #review → #manual 마지막 절 → #models
- 보여줄 내용: 오류별 복귀, 대표 결정과 현장 검증, 업데이트 프롬프트, 모델별 공식 가이드
- 확인할 결과: 작업현황·검토 기록·업데이트확인·다음 작업 조건

검토 기록에서 해결한 문제와 미해결 항목을 구분합니다. 웹 기록은 교육용이며 로컬 AI 결과와 자동 동기화되지 않습니다. 회사자료는 승인 후 갱신하고 설정 업데이트는 별도 백업·비교 후 적용합니다. 모델이 바뀌어도 회사자료·사실·검토 기준은 유지합니다.

현장 설치·실시간 생성 시연 없이 화면과 준비된 파일로 설명. 수강생은 강의 후 패키지를 적용.
